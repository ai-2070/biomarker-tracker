# CLAUDE.md

Working name: **Biomarker Tracker** (rename later).

A free, open-source, local-first web app where anyone can track their bloodwork over years, understand it in plain language, see their biological age, and explore what research says about each marker. No account, no cloud backend. Users' health data stays on their device unless they ask the assistant, which sends it to the AI model they chose (EU/US zero-data-retention providers or a local model).

---

## Core principles (never violate these)

1. **Local-first.** All user data stays on the user's computer. With the local server (`apps/server/`, 127.0.0.1 only) each person is a **profile folder** on disk (see "Profiles"); without it (a static copy of the app) there is one profile in the browser (IndexedDB). No cloud backend, no database server, no user accounts.
2. **No telemetry.** No analytics, no tracking pixels, no error reporting services, no third-party scripts beyond what is listed in this file. Developer tools too: turbo runs with `TURBO_TELEMETRY_DISABLED=1` (root scripts and CI, checked by `tests/server/devTelemetry.test.ts`; set it yourself when calling `turbo` directly), and eve's build sets `EVE_TELEMETRY_DISABLED=1`.
3. **Allowed network calls only:**
   - Europe PMC REST API (research search, open-access full text)
   - NCBI E-utilities / PubMed (research search, backup)
   - ClinicalTrials.gov API v2 (ongoing trials)
   - The AI provider the user configured themselves: EU/US providers with zero data retention (Anthropic, OpenAI, Mistral, or an OpenAI-compatible endpoint whose region the user states), OpenRouter with zero-retention routing forced on every request, or a local model (Ollama, LM Studio). Called by the local server, never by the page.
   - Agent programs the user installed and signed into (Claude Code, Codex, Hermes, OpenClaw). The app can't check what their login keeps, so they are labelled "depends on your login" everywhere they appear (the user's decision, 2026-10-28).
   - OpenRouter's public model lists (`/api/v1/models`, `/api/v1/endpoints/zdr`) to show only models with zero-retention endpoints.
   - MCP servers the user switched on in Settings (medical/nutrition only, see `packages/shared/src/core/mcpPresets.ts`); each preset lists what it sends.
   - Developer-only CDC NHANES downloads (`wwwn.cdc.gov/.../nhanes/public/`) and NCHS public linked-mortality files (`ftp.cdc.gov/.../datalinkage/linked_mortality/`): needed to fit and evaluate joint mortality coefficients from one cohort. No app/profile data is used; raw public respondent files stay in an external local cache and are never committed. The shipped app never calls these endpoints.
   - Developer-only official population life tables: Eurostat `demo_mlifetable` (`ec.europa.eu/eurostat/api/`), CDC/NCHS national tables (`www.cdc.gov/nchs/data/nvsr/`, `ftp.cdc.gov/pub/Health_Statistics/NCHS/Publications/NVSR/`), ONS downloads (`www.ons.gov.uk/file`), Statistics Canada table CSVs (`www150.statcan.gc.ca/n1/en/tbl/csv/`), ABS life-expectancy datacubes (`www.abs.gov.au/statistics/people/population/life-expectancy/`), Stats NZ period-table downloads (`www.stats.govt.nz/assets/Uploads/`), and Japan MHLW life tables (`www.mhlw.go.jp/toukei/saikin/hw/life/`). These public aggregates supply country population references; no profile data is sent, and the shipped app never calls these endpoints.
   - Desktop app updates only: the Tauri shell (not the page or the server) downloads `latest.json` and the signed update from this repository's GitHub Releases (`github.com/ai-2070/biomarker-tracker/releases/latest/download/…`), 30 s after start and every 6 h, and installs only after the person confirms. Needed so installed apps get fixes; nothing about the person is sent, and the signature is checked against the public key in `tauri.conf.json` (2026-11-04).
   - Nothing else. Any new endpoint must be added to this list in a PR with justification.
4. **Code does the math, the model does the explaining.** Unit conversion, trends, reference-range checks, and scores (PhenoAge) are computed in tested TypeScript. The LLM never computes numbers that are shown as facts.
5. **Every claim needs a source.** Knowledge base entries must include citations. AI answers may only cite papers that were retrieved and passed in context; the app verifies every cited ID against the retrieved set and strips or flags anything else.
6. **Explain, don't prescribe.** The app shows what markers mean, what is known to affect them, and the evidence strength. It never diagnoses, never tells a user to start/stop a medication, and never gives a personal dose. Anything clearly out of range shows "discuss with your doctor."
7. **Works without AI.** Tracking, charts, PhenoAge, and the knowledge base must be fully usable with no model configured. AI is an optional layer. The one exception is reading photos and scanned PDFs, which Brain does (the user's decision, 2026-11-05); typing values in, text PDFs and pasted text work without a model, and the Import page says so when no model can take pictures.
8. **Honest about what is unknown.** Biology is mostly unmapped (nutritional dark matter, unidentified metabolites, unnamed signaling molecules). The app shows what is measured and what the evidence says, labels the gaps, and never presents a prediction as a simulation of the body.
9. **Usable by non-technical people.** Plain language, large touch targets, no jargon without an explanation, works on a phone.

With the local server (`apps/server/`, Bun, 127.0.0.1 only) it gets profile folders and Brain; the desktop app (`apps/desktop/src-tauri/`, Tauri 2, `docs/desktop.md`) bundles both, with signed updates. Neither is a cloud backend.

Keep dependencies minimal. Prefer writing 30 lines over adding a package.


- `@bt/shared` is TypeScript source exported by subpath (`"exports": { "./*": "./src/*.ts" }`): import `@bt/shared/core/units`, never a relative path into another package. Inside a package, imports stay relative.
- **API (tRPC, the user's request, 2026-11-05):** the page's JSON calls go to `/api/trpc` (`@trpc/server` 11, `createHTTPHandler` in `apps/server/http.ts`, no batching, no transformer). `packages/shared/src/api/router.ts` holds the procedures and their zod input checks; the server implements `ApiServices` (`apps/server/api.ts`), so the page imports only `type AppRouter` and never server code. The page's client is `localServer` in `apps/web/src/app/api.ts` (`httpLink`, always sends `x-bt: 1`). Queries are GETs, mutations POSTs; the Host and `x-bt` checks run before tRPC, and mutations are refused as GETs. Errors with a `status` (`ProfileError`, `HttpError`, `ClaimEvidenceError`) keep it (400/403/404/413/500) and their plain message; invalid input gets a plain sentence, never schema issues or stack traces. Still plain HTTP: `/api/assistant` (streaming), profile file uploads/downloads, backups and restore, `/mcp`, `/eve-bridge`. Tests: `tests/server/trpc.ts` (real HTTP), `tests/app/fakeServer.ts` (stubbed fetch in tRPC format, `mockApiModule`).
- `bun dev` (`turbo run dev`) builds the eve runtime, then runs the page (Vite, hot reload) and the local server together (`bun --watch`: restarts on changes; Bun restarts right after SIGTERM, so `index.ts` stops owned process trees synchronously first); `BT_PORT` moves the server and the page's `/api` proxy. `bun run desktop:dev` adds `src-tauri/tauri.dev.conf.json`: `bun dev` as the before-command, the window on Vite's `devUrl` (`strictPort` under Tauri, so it never opens another copy), no sidecar or resources, profiles in `data/`; the bundled server path stays for builds and `bun run tauri dev`. `bun run build` runs typecheck plus the web and eve builds; `bun run typecheck` checks every package and `tsconfig.json` (tests, tools).
- The server finds `knowledge/`, `skills/` and `data/` at the repository root (`ROOT` in `apps/server/store.ts`, or `BT_ROOT`), the page in `apps/web/dist` (`BT_DIST`) and eve in `apps/eve/.output` (`BT_EVE_ENTRY`).

Everything in `packages/shared/src/core` must be pure functions with tests. UI never does math directly.

## Data model

```ts
// Shipped with the app, in /knowledge/biomarkers/*.json
interface BiomarkerDef {
  id: string;                 // "ferritin", "hba1c", "crp_hs"
  name: string;
  abbreviation?: string;      // "HbA1c"; shown with the full name once
  category: string;           // "Blood count", "Lipids", ... (see packages/shared/src/core/types.ts)
  aliases: string[];          // names labs use: "Ferritin", "Ferritin (S)", "Ferritin szérum"
  loinc?: string[];
  canonicalUnit: string;      // all values stored in this unit
  conversions: Record<string, number | { factor: number; offset: number }>; // unit -> canonical; offset form needed for HbA1c mmol/mol
  defaultRanges?: { low?: number; high?: number; sex?: "m" | "f"; fasted?: boolean; ageFrom?: number; ageTo?: number }[]; // canonical unit; lab range wins; ages at the date measured
  judgeAverageOfDays?: number; // sleep: the range is checked against this many days' average (`flagLatest`), single readings only when critical
  personalRange?: boolean;    // HRV: no population range; the person's own usual range instead (`personalRange.ts`)
  criticalRange?: { low?: number; high?: number }; // beyond this: urgent "contact a doctor" banner
  rangeNote?: string;         // e.g. "fasting sample"
  summary: string;            // plain language, 1–3 sentences
  high: { meaning: string; commonCauses: string[] };
  low:  { meaning: string; commonCauses: string[] };
  affectedBy: EvidenceRef[];  // links to /knowledge/evidence entries
  sources: Citation[];        // required, at least one
}

// Stored in IndexedDB
interface Measurement {
  id: string;
  biomarkerId: string;
  value: number;              // in canonical unit
  originalValue: number;
  originalUnit: string;
  qualifier?: "<" | ">";      // lab printed "<0.1" (e.g. below detection limit)
  date: string;               // ISO date of sample
  lab?: string;
  labRange?: { low?: number; high?: number };
  fasted?: boolean;
  source: "manual" | "pdf" | "csv";
  note?: string;
}

interface ProtocolEntry {      // supplements, diet changes, meds the user logs
  id: string;
  label: string;              // "Creatine 5 g"
  category: "supplement" | "diet" | "medication" | "lifestyle";
  start: string;
  end?: string;
}

interface EvidenceClaim {      // /knowledge/evidence/*.json
  id: string;
  intervention: string;       // "omega-3 (EPA+DHA)"
  outcome: string;            // "triglycerides"
  direction: "increase" | "decrease" | "no effect" | "mixed";
  grade: "high" | "moderate" | "low" | "very low";
  whyThisGrade: string[];     // "mostly small trials", "industry funded", ...
  studies: Citation[];
}

interface Citation {
  pmid?: string;
  doi?: string;
  title: string;
  year: number;
  studyType: "meta-analysis" | "rct" | "observational" | "animal" | "in vitro" | "review" | "guideline";
  n?: number;
}
```

## PhenoAge (Levine et al., 2018)

Inputs (convert to these exact units first):
albumin (g/L), creatinine (µmol/L), glucose (mmol/L), CRP (mg/dL, natural log), lymphocyte (%), MCV (fL), RDW (%), alkaline phosphatase (U/L), WBC (10³/µL), chronological age (years).

```
xb = -19.907
     - 0.0336  * albumin
     + 0.0095  * creatinine
     + 0.1953  * glucose
     + 0.0954  * ln(CRP)
     - 0.0120  * lymphocyte_pct
     + 0.0268  * MCV
     + 0.3306  * RDW
     + 0.00188 * ALP
     + 0.0554  * WBC
     + 0.0804  * age

gamma = 0.0076927
M = 1 - exp( -exp(xb) * (exp(120 * gamma) - 1) / gamma )
PhenoAge = 141.50225 + ln( -0.00553 * ln(1 - M) ) / 0.090165
```

- **Verified 2026-10-28** (see header of `packages/shared/src/core/phenoage.ts`): weights match the paper's Table 1 (PMC5940111) and BioAge R (`phenoage_calc`, `orig = TRUE`). Tests use pyaging's R-computed reference values (log hazard −12/−9/−6 → 9.375/42.647/75.920 years) and a transcription of BioAge as an oracle. Do **not** use biolearn as a reference: its RDW weight is 0.3356 (typo).
- Implementation uses the algebraically equal stable form `141.50225 + (xb + ln(0.00553·(e^{120γ}−1)/γ)) / 0.090165`, which stays finite when M rounds to 1.
- Age comes from birth **month and year** only (`Profile.birthMonth`, "YYYY-MM", mid-month assumed). Not shown under age 20 (model trained on adults).
- Only compute when all 9 markers come from the **same blood draw**.
- Guard CRP ≤ 0 (lab "<0.1" values): use the detection limit and mark the result as approximate.
- Show it as an estimate with a short explanation, never as a verdict.

## Expiration date (life tables)

- **Country population reference is always available** on Biological age (`components/dashboard/CountryPopulationReference.tsx`), independent of `showExpirationDate`: median age reached, mean remaining years, middle-half age span and a conditional-survival chart (`populationSurvival` in `packages/shared/src/core/lifeTable.ts`, tested). It starts with 100 people alive at the person's current calendar age, marks **Your age**, and shows how many survive to later ages at the source period's rates. Solid through 95, dashed for the exponential tail; keyboard tooltip and a table view. Never a personal percentile or a fitted-risk curve. With dates off, no exact future calendar date, fitted model or Easter egg is loaded/shown. Brain's independent `countryPopulationReference` gives the same statistics/curve/source; `expirationDate` remains off and must not be guessed.
- **Compare countries** (`dashboard/CountryComparison.tsx`, `compareLifeTables` in core, tested): all supported tables ranked by mean remaining years at the same calendar age and sex, zero-based bars and numeric labels, saved country highlighted, individual reporting periods and expandable source/scope notes. An accessible ordered list in a keyboard-scrollable region includes every row; missing combined-sex tables are explicitly named, never substituted. Not a same-year ranking, healthcare score or causal effect of moving. The Country population reference block sits immediately before Heart age, after the PhenoAge explanation; within it, the person's survival curve precedes Compare countries. The optional Expiration date is independently mounted at the top of the page above Ages (`dashboard/ExpirationDate.tsx`); both sections share the validated bundle through `app/lifeTables.ts`, while fitted code/models and the Easter egg remain opt-in.
- The separate "Expiration date" card (first called "Best before") remains **off by default**, enabled per profile in Settings → Appearance (`showExpirationDate`, `useShowExpirationDate`). It is lazy-mounted only when on and the reference inputs are available (`components/dashboard/bestBefore.tsx`): exact dates to the second in the person's time zone, the experimental projection when supported, the unshifted date beside it, limits and the existing Easter egg. No countdown. Seconds are calculation precision, not prediction precision.
- **Data:** `knowledge/lifetables/countries.json`, built by `tools/lifetables/build.ts` with the release-pinned national Python importers (`requirements.txt`, developer-only). Per-country source URL, retrieval date, reporting period and scope/provisional notes; survivors lx at every exact age 0–95, normalized to 100,000 births, and native remaining life expectancy at 95. Eurostat covers 31 EU/EFTA countries and the EU average (2024; Netherlands 2023); CDC/NCHS the US (2024), ONS the whole UK (2022–2024), Statistics Canada (2024, preliminary), ABS Australia (2022–2024), Stats NZ (2022–2024), and MHLW Japan (2025, Japanese nationals in Japan, provisional). No invented combined-sex tables for UK/Australia/NZ/Japan: missing sex is requested in Settings. The app makes no statistical-office network calls. The builder rejects missing countries, sexes, ages or invalid distributions before publication; source lx/ex means are checked against native e0/e65 values.
- The optional profile `country` uses `LIFE_TABLE_COUNTRIES` (Eurostat's EL retained; UK is GB). The population card shows `InlineCountry` only when country is missing/unsupported: draft choice plus explicit **Save**, then the form disappears. `saveCountry` in `apps/web/src/db/db.ts` transactionally checks profile identity, rereads blanks and preserves concurrent profile edits; Settings still changes an existing country. Country changes select a population baseline only, never country-specific fitted coefficients.
- **Maths** (`packages/shared/src/core/lifeTable.ts`, tested): lx joined by straight lines, past 95 a constant death rate 1/e95; the ages by which a quarter, half and three quarters of the people alive at an age have died (`bestBefore`), mean remaining life expectancy, and conditional survival `100 × lx(later age) / lx(current age)`. Moments use the middle of the birth month (`momentAtAge`), with age taken at the start of today so optional dates hold still through the day.
- **Jointly fitted mortality model** (2026-11-01): `tools/longevity/train.py` fits weighted ridge Cox models to public NHANES 1999–2004 examinations and NCHS 2019 public linked mortality, with an untouched 2005–2006 temporal holdout. `knowledge/models/mortality.json` ships aggregate coefficients, actual centering and ten-year baseline hazards; `tools/longevity/evaluation.json` records source checksums, development-only three-fold penalty selection, held-out Brier/AUC, calibration, paired PSU-within-stratum bootstrap intervals and synthetic native-lifelines inference oracles. Five DXA imputations are fitted separately and predictions pooled, never stacked as independent people or averaged as measured fat. Early-cycle MEC weights and creatinine assay corrections follow CDC documentation. Complete cases are not claimed nationally representative. No raw participant rows, private machine paths, AI calls or runtime Python dependency.
- **Supported inputs:** age, sex and cigarette-smoking status, plus independently fitted variants for body-fat percentage + waist-to-height (ages 20–69), clinical PhenoAge gap from all nine markers on one draw, or blood + smoking without body measurements (ages 20–84). Optional actual moderate-or-harder leisure-exercise minutes in sessions of at least ten minutes, vigorous counted once; generic device active time is not silently substituted. `mortalityActivityIsLeisure` is a default-false profile setting with explicit confirmation on the card, included in Brain's snapshot. At least 21 distinct daily totals in the last 30 days; missing days are not zero. Resolve persisted same-day winners before excluding bounded/invalid totals. Resting overnight RMSSD, DunedinPACE (not DunedinPoAm), and incompatible strength/balance/walking tests have no fitted weight and are shown as not included, not unimportant.
- **Shared inference and lifetime transport:** `packages/shared/src/core/mortalityModel.ts` validates artifacts, evaluates centered Cox probabilities and inverts the same-cohort age/sex comparison to a risk-equivalent age; `mortalityProjection.ts` supplies the same dated inputs and outputs to the page and Brain. No missing-value normal assumptions, guessed weights, unsupported predictor ranges or age extrapolation. Readings may be carried forward at most 365 days; body-fat/waist pairs must be within 30 days, labs/body within 90 (availability choices, not validated cutoffs). Only a positive `<CRP` detection limit is accepted as an approximate bounded blood input. When eligible, `bestBeforeWithShift` reads the country table at fitted risk-equivalent age and assumes its gap persists; the plain country reference is always retained. The old PhenoAge-only shift and averaging helper are removed.
- **Limits on the card:** this is an app-fitted research score, not a clinically validated personal-risk calculator or prediction of death. All six variants improved the prespecified held-out Brier/AUC comparison against age/sex alone, but mean risk was overpredicted; predicted versus observed rates are shown, not hidden behind the discrimination metric. Ten-year testing does not validate transfer to another country, home body-fat methods, recorded activity or a lifetime date. The middle-half range is a population spread, not a personal confidence interval; no causal years gained. Brain's `get_biological_age` returns the same calculation, input exclusions, calibration and limits; when off it returns no date. Newly created example profiles live in Austria. **Easter egg** (the user's idea and wording): about once in 50 mounts the headline date becomes tomorrow at a random time, with “Cause: car crash.” and a hover/tap “Easter egg (1 in 50)” popover. Only the headline changes; explanatory text names the real median. No separate setting.

- **What has moved these clocks** (the user's request, 2026-10-30): `knowledge/clocks/interventions.json` (`ClockFile` in `packages/shared/src/core/clocks.ts`, validated, tested in `tests/knowledge/clocks.test.ts`): 12 interventions tested against PhenoAge, DunedinPACE or methylation clocks in people, graded findings with label and line, `clocks` naming which ones ("PhenoAge" is the app's blood-test formula, "DNAm PhenoAge" the methylation clock), and `about` links to supplement, food and lifestyle pages. Shown on the Biological age page under a caveat (stand-ins; nobody has shown lowering them adds years; colds and glucose move PhenoAge by arithmetic), and as an "Aging clocks" note on the linked pages (`ClockEvidence`, `ClockNote`). Null results are included (vitamin D, exercise, cocoa, Mediterranean diets, metformin). Written by a research agent, every citation checked against Europe PMC; not yet reviewed by a clinician.
- **Watching PhenoAge in Habits** (the user's request, 2026-10-30): a derived marker, "PhenoAge gap" (`packages/shared/src/core/phenoageWatch.ts`, tested): PhenoAge minus calendar age at each blood test with all 9 markers, never stored, added to the person's results only for habit watches (`useWatchMeasurements`, `WATCH_DEFS`, `watchDef`). Offered in the marker picker once there's a complete PhenoAge test. Compared as a plain difference in years (`changeScale: "difference"` on `BiomarkerDef`; `analyzeMarker` → `analyzeDifference`), with noise from the person's own gaps before the start, from one test to the next (mean successive difference, so a slow real trend isn't counted as noise; `differenceBand`, at least 3 tests; t table now from 1 degree of freedom). One test on each side gives a wide band (the example: ±6.2 years), and the page says lowering the gap hasn't been shown to add years.

## Pace of aging

- A "Pace of aging" card on the Biological age page (`components/dashboard/agePace.tsx`), two measures shown apart, never averaged:
  - **Pace of your PhenoAge** (`packages/shared/src/core/agePace.ts`, tested): the least-squares slope of PhenoAge against calendar time over the tests in the last 3 years (at least 3 tests over a year or more; 14 days of slack for test dates), with a 95% interval (t, n − 2). Verdict only when the whole interval agrees: falling (top below 0), slower (top below 1), faster (bottom above 1), otherwise unclear. Labelled as computed by the app and not DunedinPACE.
  - **DunedinPACE** (`knowledge/biomarkers/dunedinpace.json`, category "Aging"): a DNA methylation blood test from a specialised lab (Belsky et al., eLife 2022, PMID 35029144; Pace of Aging, PNAS 2015, PMID 26150497). The app only records the reported number (typed in, or read from a report: one unit, assumed when none is printed) and never calculates it: its code is for research use only and needs methylation array data. No clinical range.
- **DunedinPACE scores** (`dunedinSummary` in `packages/shared/src/core/agePace.ts`, tested; `DunedinScores` on the DunedinPACE page and in the Pace of aging card): the plain average of the tests in the 2 years up to the latest (tests under 4 years old), and the Rejuvenation Olympics leaderboard rule ("average pace from best 3 tests over 2 years", at least 3 tests; rejuvenationolympics.com/dunedin-pace, read 2026-10-29), with a note that the best 3 always sit at or below the average. Their leaderboard (names, values) is not copied into the app. The example profile has three DunedinPACE results.
- Not added: WHOOP Age and WHOOP's "Pace of Aging" (a company white paper, not validated, overlap corrections unpublished; adding hazard ratios from separate studies is a combined score, which this app avoids). Decided 2026-10-29.
- Brain's `get_biological_age` returns both (`phenoAgePace` with its range and verdict; DunedinPACE results as recorded). The example profile has two made-up DunedinPACE results on its blood draws.

## Heart age (Framingham, body data)

- `packages/shared/src/core/heartAge.ts` (tested): Framingham general CVD risk, office-based model with BMI (D'Agostino 2008, PMID 18212285); coefficients from the Framingham Heart Study's site and its `gencardio_bmi.xls` (checked 2026-10-29). Heart age = the age at which normal risk factors (systolic 125 untreated, BMI 22.5, non-smoker, no diabetes, the calculator's reference values) give the same 10-year risk; closed form. Tests use the calculator's own example (woman, 30, normal factors → risk 0.010801167676829593, heart age 30).
- Inputs: sex, age from birth month, systolic = average of readings in the 30 days up to the latest, BMI from latest weight and height, smoking from the profile; blood pressure treatment and diabetes from the profile's conditions or active medicines in Habits (shown with where they came from). Only ages 30–74. Shown on the Biological age page (with the predicted 10-year risk, inputs and limits; a risk of 20 % or more suggests discussing it with a doctor) and as a figure on the Body page.

## Fitness age (VO₂max, body data)

- `vo2max` is a body measurement (mL/kg/min; imported from Apple, Garmin, Fitbit, Oura and other exports, or typed in). `packages/shared/src/core/fitnessAge.ts` (tested): mean VO₂max of healthy adults by sex and age group from the HUNT 3 Fitness Study (Loe et al., PLoS One 2013, PMID 23691196, Table 2, open access; values copied, not estimated). Fitness age = the age at which they averaged the same VO₂max, group means at mid-group ages (25…75) joined linearly; above the youngest or below the oldest group it says "25 or younger" / "75 or older" instead of extrapolating. The Nes 2011/2014 non-exercise formulas were not used: not open access and corrected in 2020.
- Brain's `get_body_summary` tool (`packages/shared/src/core/bodySummary.ts`, tested) gives the app's own BMI, waist-to-height, basal metabolic rate, heart age with 10-year risk, fitness age, and recent averages, so the model reports them instead of calculating.

## Fitness tests (age-related, body data)

- Seven tests in `/knowledge/fitness/<id>.json` (`FitnessTestDef`, validated by `validateFitnessTest`, tested in `tests/knowledge/fitness.test.ts`), each also a Body marker with the same id: `pushups`, `grip_strength`, `sit_to_stand_5x` (lower is better), `chair_stand_30s`, `one_leg_stand`, `gait_speed`, `sitting_rising`. Each file has the how-to, safety, limits, graded evidence with verified citations, norm tables and cut-offs. Written 2026-10-29 from research agents' drafts (`scratchpad` builders), every value copied from its source; grades not yet reviewed by a clinician.
- Norms: grip Dodds 2014 (Britain, best of either hand, exact-age rows: the nearest tabulated age is used, `rowSpan`); walking speed NIH Toolbox 4 m (US, mean ± SD); five chair rises SHARE (Europe 50+) and pooled Asian cohorts (20+), performance-ranked percentiles turned into value percentiles; 30-s chair stand Poland (60+) and Colombia (18–80, middle percentiles only); one-leg stand Iran (right leg, 60 s limit) and the British 1946 cohort (30 s limit; results capped at a study's `ceiling`); push-ups CSEP (book table read from an authorised reprint; men from the toes, women from the knees); sit-and-rise Brito 2014's four score groups (51–80, from the abstract). **Not used:** the user's Blueprint push-up chart (source untraceable, women's numbers converted from knee push-ups) and Blueprint's sit-and-rise grid (read off an image); PURE grip (a different way of measuring).
- Core (`packages/shared/src/core/fitnessTests.ts`, tested): `normRow`, `placeInRow`, `placeResult` (only norms for the test's way of doing it, `defaultVariant`), `cutoffsMet` (EWGSOP2 grip and walking speed, Dodds weak grip, five rises over 15 s, one-leg under 10 s at 51–75), `describePlace` (percentiles said so that higher is better, also for timed tests), `fitnessSummary` (Brain's `get_body_summary`), and Bryan Johnson-style comparisons kept honest: `ageMatch` ("typical of women about 45": the age whose median or average equals the result, only after the table's best age, ages joined by straight lines, `youngest` when the best is the table's first row, never past an open "and over" group) and `placeAmongYoungest` (place among the youngest group, e.g. 20–29). No combined score across tests (different tables, methods and evidence; no validated weighting) and nothing finer than the tables' last percentile (no "top 1%").
- UI (`components/dashboard/fitness.tsx`, `components/NormChart.tsx`): Body page group "Strength, balance and walking" (figures with the place for age), each test's page "For your age" (`?section=for-your-age`: place per norm table, cut-offs as a notice to mention to a doctor, the norms drawn across age with the person's results as dots and the copied table with their row marked, how-to, safety, limits, evidence), "Tests for your age" on the Biological age page, a section in the body entry form. The example profile does the tests every 8 months.
- Waist-to-height has its own figure and panel (see Body measurements); BMI and resting metabolic rate open a window with the sum worked through.

## AI layer (local server, v0.9)

One assistant, no teams or multi-agent setups. Model choice, Skills and MCP settings work like Blacksite's, limited to medical and nutrition use.

- **Local server** (`apps/server/`, `bun run server` / `bun run start`): node:http on `127.0.0.1:4820`. Checks the Host header; changes need the `x-bt: 1` header and are refused from other sites. The JSON API is tRPC at `/api/trpc` (see Repo structure). Settings in `data/settings.json`, keys in `data/secrets.json` (mode 600, never returned to the page, never in backups). `data/` is gitignored. In dev, Vite proxies `/api` to it.
- **Models** (`packages/shared/src/core/aiProviders.ts`, `apps/server/models.ts`): Vercel AI SDK. `canUse()` allows local models on localhost, cloud providers with a key, an EU/US region and zero data retention confirmed by the user, and OpenRouter with a key (`apps/server/openrouter.ts` adds `provider: { zdr: true, data_collection: "deny" }` to every request body). OpenAI uses Chat Completions with `store: false`. Errors are described in plain words, with keys redacted.
- **Choosing a model** (`packages/shared/src/core/aiProviders.ts`): providers are listed agent programs first, then API-key providers, then local models (`group`). The default, until something is saved, is Claude Code with `opus` (`DEFAULT_CHOICE`, `currentChoice()` on the server). Model lists were checked 2026-10-28; OpenRouter, Ollama, LM Studio and Hermes profiles / OpenClaw agents are loaded live. **Effort** (`low`…`max`, only the levels each provider lists in `efforts`): Claude Code `--effort`, Codex `model_reasoning_effort`, Hermes `--reasoning`, OpenClaw `--thinking`, Anthropic `effort`, OpenAI and Mistral `reasoningEffort`, OpenRouter `reasoning.effort`.
- **Installing agent programs**: each has `install` (the maker's official Windows and macOS/Linux commands, sign-in command, docs). The Install and Sign in buttons open a visible terminal (`apps/server/terminal.ts`) running only those fixed commands; nothing is installed silently. `which()` also reads the current PATH from the Windows registry and the installers' usual folders, so a fresh install is found without restarting.
- **Agent programs** (`apps/server/agents.ts`): one process per question in an empty temp folder, with the conversation as text. Claude Code: `-p --output-format stream-json`, `--system-prompt-file`, `--tools ""`, `--strict-mcp-config`, only `mcp__bt` allowed. Codex: `exec --json --sandbox read-only`, bridge token via `bearer_token_env_var`. Hermes: `chat --query-file - --format stream-json`; gets the app's tools only after the user presses Connect (runs `hermes mcp add biomarker-tracker --url …?token=…`). OpenClaw: `agent --json --message-file`, no bridge, so it gets a data summary (`dataPack`) and its citations are marked as uncheckable. Time limit 10 minutes, no turn limit. Each program runs in its own process group (`apps/server/processTree.ts`): Stop, the time limit and server shutdown send SIGTERM to the whole group and SIGKILL to whatever is left after 3 s (Windows: `taskkill /t`); helpers a program leaves behind when it finishes are stopped too; the server kills any group it still owns when it exits. Tested with real processes (`tests/server/processTree.test.ts`).
- **Bridge** (`apps/server/bridge.ts`): the app's tools as an MCP server over HTTP at `/mcp` (stateless Streamable HTTP). Each question opens a run with a random 32-byte token that dies when the answer is done; Hermes uses a stable token (`secrets.bridgeToken`) that only works while a Hermes run is active. `/mcp` skips the `x-bt` check but needs the token and the Host check. Tool calls are recorded as steps, and study IDs come from their results, so citations are verified the same way for agents.
- **Assistant** (`apps/server/assistant.ts`, `apps/server/healthTools.ts`): the page sends a snapshot of measurements, log, experiments and profile with each question; the server turns birth month into age and never passes birth month to the model. Tools: get_results, get_marker, get_levers, get_biological_age, get_log, compare_before_after, search_research (Europe PMC), get_study (one study by PMID/PMCID/DOI from Europe PMC, with its abstract; used by the "Summarize with Brain" button on each paper in a marker's research results, which sends the question once a model is ready, and isn't shown next to a critical result), read_skill, propose_habit (a habit card the person edits and confirms in the chat; never a medicine, never an amount (`DOSE`), at most 5 watched markers, not next to a critical result; checked by `parseHabitProposal` in `packages/shared/src/core/habitProposal.ts` on the server and again in the page, which builds the card from the tool step, `habitTurns` in `brain/store.ts`; nothing is saved until the person presses Add to Habits), plus tools from enabled MCP servers (`server__tool`). get_log returns the person's Habits (with watched markers) and Brain calls them habits. All numbers come from `/core`. **No step limit** (API models loop until the model stops calling tools, `isLoopFinished`; claim checks also stop once their assessment is submitted) and **one 10-minute limit** for every path (`ASSISTANT_TIMEOUT_MS`). `apps/server/assistant.ts` is the entry point; the parts live in `apps/server/brain/` (`ask.ts` modes and engines, `prompt.ts`, `cache.ts`, `tools.ts`, `apiModel.ts`, `agentRun.ts`, `claimReview.ts`, `dataPack.ts`).
- **Streaming** (the user's request, 2026-11-04, after ai-dashboard): every engine reports the same events (`apps/server/brain/events.ts`: text, tool started/finished with study IDs, status). API models use `streamText`; Claude Code runs with `--include-partial-messages`, Codex and Hermes are read line by line; the bridge reports tool calls as they run. `apps/server/uistream.ts` writes AI SDK `UIMessageChunk`s as SSE (dynamic tools, transient `data-status`, `data-studies`, final `data-reply` = the same verified envelope as the JSON reply). `/api/assistant` streams for `Accept: text/event-stream` and still answers JSON otherwise. The page reads it with `DefaultChatTransport` + `readUIMessageStream` (`apps/web/src/app/brain/stream.ts`, loaded with the first question) into a live turn: text since the last tool, citations checked only against studies returned so far, tools as they run; the checked reply replaces it, Stop or an error drops it. Closing the stream stops the run and its programs.
- **Prompt cache** (`apps/server/brain/cache.ts`): the system prompt is a stable part (rules, skills index, research servers) and a short per-request part that always comes last (critical results, cautions, the evidence-check date). The tool list is the same on every turn in a fixed order (`save_profile_details` is always offered and refuses without typed text; research-server tools last, without server ids in descriptions). Anthropic: cache points on the stable part and the newest message; OpenAI: stable `promptCacheKey`; OpenRouter: stable `session_id` and `cache_control` for Anthropic models. Agent programs get stable rules, the tools note, then the request part. Known misses: the turn after a photo (it isn't re-sent), and agent programs start fresh per question (no session files with health data).
- **eve engine** (opt-in preview, the user's choice 2026-11-04; Settings → AI models → Run in eve, `settings.eve`): API-key and local models answer inside eve (`eve` 1.1.0, pinned; `apps/eve/agent`, built by `bun run eve:build`). A private child process on 127.0.0.1 (`apps/server/eve/host.ts`, owned process tree, new tokens each start, run store `data/eve/`, telemetry off). The agent is a thin shell: rules, tools and every model call come from the main server over the token-checked `/eve-bridge/*` (`apps/server/eve/bridge.ts`), so keys, zero-retention routing, provider options and cache points stay in one place; eve makes no network calls of its own. One session per question, earlier turns imported as history, ended after the answer with `retention: 0` (run data deleted). Claim checks and questions with photos keep the built-in loop. Tests run the built runtime end to end with a mock model (`tests/server/eve.test.ts`).
- **Conversational personal-data capture** (`packages/shared/src/core/profileCompletion.ts`, `packages/shared/src/core/measurementCompletion.ts`, `fillPersonalDetails` in `apps/web/src/db/db.ts`): common first-person profile facts and explicit current readings are detected from the newest typed message without model tool calls. Profile parsing handles comma-separated introductions, common diet qualifiers and spelling errors; measurement parsing also accepts “im”, value-first “27% body fat”, bare self-reported weight with kg/lb, and named markers via the existing lab parser's aliases. Units, conversions, plausible body limits and blood-pressure pairs use the existing manual/body validators. The “pace of aging” alias maps to a reported DunedinPACE reading with its single unit; derived PhenoAge pace, BMI, heart age and fitness age are never stored this way. No capture from attachments, quotes, other people, hypothetical/goal/past values or opt-outs; age never becomes an invented birth month. Server tools see request-local detected data before answering. After a successful personal reply, one transaction checks profile identity and cancellation, re-reads current profile blanks and same-marker/date entries, and saves only missing data. Same-day values and concurrent edits win; new dates can add readings. “Added to your profile”/“Saved measurements” receipts show only committed additions, their date and result links. Existing Dexie folder sync handles disk persistence; models never write profile files or invent a save. `save_profile_details` can still supply additional validated first-person quotes. Research-only conversations remain read-only.
- **Changes on request** (the user's decision, 2026-11-27: Brain should save, start, edit and delete almost anything when asked, and speak as the app itself): `change_data` (`apps/server/healthTools.ts`) adds, corrects or deletes results (by id, or marker and/or date); starts, edits, stops or deletes habits (the person's own medicines and amounts included, copied as said: recording isn't advice); starts, stops or deletes saved protocols; deletes meals; sets or overwrites profile fields (`BRAIN_PROFILE_FIELDS`: never name or private notes); and saves the open review card ("save them" bumps `saveRequest`, the card saves itself exactly as if Save was pressed). Every call quotes the person's words, which must appear in the newest typed message (`userText`), so pictures, files and research text can never trigger a change. One pure function, `applyChanges` in `packages/shared/src/core/brainChanges.ts` (tested), checks and applies them all or nothing; the server runs it on the snapshot (later tools see the result) and the page runs it again on the current data after the answer (`applyBrainChanges` in `apps/web/src/db/brainChanges.ts`, one transaction, identity-checked), diffing every table into an exact Undo record. The receipt (`turns/ChangesTurn.tsx`) lists what was actually written, with one Undo that never overwrites rows edited since (`undoBrainChanges`). Refusals explain why and list ids/dates so the model can retry. Medicine and critical-result limits apply to Brain's own suggestions (`propose_*` with `intent: "recommend"`), not to what the person tells it to record; a critical result still gets the doctor advice first. Tool outputs carry ids (results in get_marker, habits, protocols, meals). Typed reading capture skips messages about deleting or correcting a reading. Receipts aren't kept in chat history.
- **Requested creations** (`packages/shared/src/core/assistantProposal.ts`): `propose_protocol`, `propose_meal` and `propose_habit` distinguish `intent: "record"` from `"recommend"`. Brain uses review cards for creation requests and relevant requested recommendations; nothing saves or starts before confirmation. Recorded protocol amounts must occur with their item in the current source text. Recommended protocols contain no medicines, supplement doses or food amounts; ordinary lifestyle durations/frequencies, sets and repetitions can be examples, not personalised medical targets. Habits never contain medicines or supplement doses. Meals use real food ids, code totals and example portions, with food-safety checks at proposal and save. Critical results block every proposal; safety flags block free-text nutrient-increase suggestions. SDK and bridge steps become `validated` only after matching successful built-in results. Failed calls and MCP lookalikes never count as mutation instructions. Research-only Brain has no mutation tools or client persistence.
- **System rules:** personal Brain is a practical wellness assistant: direct options, likely benefits, fit and limits first; no obligatory live paper search or complete profile for ordinary gym, food or focus guidance. App knowledge supports relevant claims; research tools are used for evidence requests, current/disputed questions or important gaps. Research-only Brain keeps the focused evidence-check workflow. Both modes cite only returned sources, never invent research, diagnose, recommend medication changes or prescribe personal supplement doses. Calculated personal numbers still come from code; explicitly stated facts may be repeated. Critical results still require contacting a doctor first. Specific risk flags remain enforced; generic doctor warnings should not crowd out ordinary answers.
- **Citation verifier:** study IDs are collected from tool results (`studyIdsIn`); `CitedAnswer` checks every cited ID with `packages/shared/src/ai/citations.ts`. Unknown IDs are struck through, author-year references flagged.
- **Skills** (`skills/<id>/SKILL.md`, custom ones in `data/skills/`): name + description front matter; the model sees the index and loads one with read_skill. Bundled skills must keep the doctor/no-dosing rule (a test checks).
- **MCP** (`packages/shared/src/core/mcpPresets.ts`, `apps/server/mcp.ts`): stdio servers via `npx -y package@pinned-version`, minimal environment, secrets kept with the server. Only medical/nutrition presets. On first start all presets are added (`ensureDefaultServers`, once; removed ones stay removed), switched on when `npx` exists and no key is required, and started in the background (`warmUp`). A question waits at most 45 s per server. The ~150 server tools are not sent to the model: it gets `research_tools` (list one server's tools) and `use_research_tool` (call one), plus a list of servers in the system prompt. Study IDs from `read_skill` and `research_tools` output never count.
- `connect-src` in `apps/web/vite.config.ts` lists only `'self'`, Europe PMC and NCBI; the page never talks to a model directly. Old browser-stored keys are deleted on start (`forgetBrowserAiKey`).

- **Editing and deleting saved results** (`components/SavedResults.tsx`, `MeasurementEditor.tsx`, `apps/web/src/db/db.ts`): Blood tests and Body offer **Manage results**; marker histories use the same selectable list. Reading details are black-and-white SVG charts of every selected reading, including body/device history, without value-by-value tables or downsampling. Bounds are arrows at reported limits; connecting lines stop at bounds and days with multiple readings. Unknown flags say “Not assessed,” not “normal”; weekly activity thresholds never become daily ranges.
  - **Optional profile information** includes latest weight on or before report end (regardless of selected markers/start date), date/unit/source, BMI without a range label and existing `bmrMifflinTerms`. BMI/RMR appear **both in Profile information and Body measurements → Size and composition**, using shared formatted values; Size and composition holds the equation inputs, age at that weight from birth month, study-age limits and estimate/not-calorie-target caveats. They are not additional stored readings or chart histories. Missing inputs or bounded weight cannot produce BMI/RMR. Turning profile details off omits all these fields. Overlapping logged habits retain grouped protocol snapshots. Profile/result/item notes are stripped unless explicitly selected.
  - **Print / save as PDF** uses the browser's native destination and a print-only React portal, with repeating patient/date/example labels in table-header flow. The first-page header has the app logo/name and a locally embedded GitHub QR (`app/assets/report-github-qr.svg`, no runtime QR dependency or health data); regenerate the asset if `REPO_URL` changes. Preview invalidates when options or source data change. No AI, external PDF service, combined score or source-data writes; works offline. Fictional example disclosure remains without profile details. This is a patient-entered/imported handout, not verified laboratory records or evidence of a habit's effect.
  - **Brain navigation:** the personal system prompt in `apps/server/assistant.ts` explains Settings → Your data → Doctor-ready report, dates/measurements/privacy options, Create doctor report, preview, and Print / save as PDF. No research or personal-data tool call is needed for this help; Brain never claims it created, attached or sent the PDF, and keeps this separate from JSON backups.
- Name and private notes are never sent to an AI model (`assistantProfile()` in the page and again in `parseSnapshot`). Pictures are the exception the person is told about: whatever is printed on a photo or scanned page they send reaches the model. ## Lab PDF import

- Extract text with pdf.js, then match lines against biomarker `aliases`, parse value + unit + range.
- Always show a **review screen** before saving: the user confirms or fixes each parsed value. Never save silently.
- **Test date first** (2026-11-27): the Import page asks for the date of the blood test before reading; empty uses the date printed on the report. The entered date wins for text PDFs, pasted text and pictures Brain reads, and the review says so when the report prints another (`withTestDate` in `labText.ts`).
- **Report-wide details** (`components/LabReview.tsx`, shared by Import and Brain): lab PDF and photo review includes sample date, lab name, fasting (Yes / No / Not sure, initially unset) and a shared optional note. Fasting and the trimmed note are saved on every selected new result; health-app screenshot review keeps its separate body wording. The mobile save bar sits above the bottom navigation.
- Parsers per lab/country live in `/src/core/importers/`, each with sample-text fixtures in tests. Never commit real patient PDFs; use synthetic or fully anonymized fixtures.
- Multiple languages matter (EU users). Aliases should include local names (German, Hungarian, etc.).
- Current implementation: `packages/shared/src/core/importers/pdfText.ts` rebuilds lines from pdf.js text positions; `labText.ts` is the generic parser (name → value → unit → range, sample date with birth-date lines excluded). Lab-specific parsers can be added next to it when a layout needs one. Fixtures: `tests/fixtures/lab-text/*.txt`.
- An alias must belong to exactly one marker (a test enforces this). Avoid aliases that are common words or that name a different test (e.g. "HbE", Hungarian "Vas").
- Rows whose printed unit doesn't fit the marker are shown but unticked, never saved by default. Exception, twins (`UNIT_TWIN`, `URINE_TWIN` in `labText.ts`): a white-cell percentage name with a count unit ("Lymphozyten 1,9 G/l") is read as the absolute count and vice versa, with a note; under a urine heading "Kreatinin"/"Albumin" are read as the urine tests. The ratio-word exclusion applies only to text after the matched name, so "Albumin/creatinine ratio" is the urine ACR while "Albumin/Globulin ratio" stays unmatched.
- **Photos and scanned PDFs** go to Brain as pictures, never to on-device text recognition (2026-11-05; tesseract.js, its bundled language files and the scan cleaning were removed). Brain proposes what it reads with `propose_results`, and the person checks each value in the same review screen (see Brain under App shell). PDFs with a text layer are still read on the device.
- **Names as labs print them** (`foldLabName`): aliases match ignoring case, accents, a dotless "ı" and spaces before "(" / "%" ("Thrombocyta szam", "Neutrophil (pero) %"). Blood specimen prefixes are skipped when the full name doesn't match ("Serum", "Plasma", "Szérum", "S-", "P-"…); urine prefixes never are. Rows under a urine heading ("Vizelet…", "Urine…", until a blood heading such as "Vérkép") go to the urine twin when one exists, otherwise they are unticked with a note. A unit cut off by the column ("ml/min/1") is read when every unit it starts converts the same (`truncatedUnit`, at least 6 characters with a "/"). Two loose numbers before the unit ("5 4", "8 140.0": a lost decimal point or a speck read as a digit) untick the row. The alias test compares folded names. Fixture: `hu-hospital-synthetic.txt` (a real layout, invented values).
- `decimalProblem` in `labText.ts`: a value more than 8× above or below the lab's own range on the same line (a lost decimal comma, e.g. potassium "5,4" read as 54) is unticked with a note, for PDFs too. It never blocks saving after the person checks it.
- Known gap: no Adobe CMaps bundled (rare CJK-font PDFs may extract garbled text). Pictures need a model that can see images; with Hermes or OpenClaw chosen, Brain refuses them.

## Safety rules

- No calorie-restriction targets, weight-loss plans, or "eat less than X" outputs.
- When a user logs or asks about a condition that changes advice (kidney disease, anticoagulants, pregnancy, diabetes medication), show a prominent "talk to your doctor" note and avoid nutrient-increase suggestions for affected nutrients (e.g. potassium in kidney disease, vitamin K with warfarin). Detection lives in `safetyNotes()` in `packages/shared/src/core/protocols.ts` (keyword lists incl. brand names); later features that suggest nutrients (v0.7) must check it.
- Critical values (e.g. potassium, sodium, glucose far out of range) show an urgent "contact a doctor" banner, no AI commentary first.
- Footer and onboarding: "Not medical advice. Not a medical device."

## Nutrition (planned, v0.7)

### The core limitation: nutritional dark matter
Food contains 26,000+ known biochemicals, but standard food databases track only ~150 nutrients (Barabási et al., Nature Food, 2019). Human blood metabolomics likewise detects thousands of signals that match no known molecule. We cannot model a food bottom-up from its molecules, and the app must never pretend it can.

### Design rules that follow from this
- **Whole food and isolated nutrient are different interventions.** "Eat strawberries" and "take vitamin C" get separate evidence claims and separate grades. Never infer a whole-food effect from a single-nutrient study, or the reverse. (Canonical warning case: beta-carotene-rich diets were associated with lower lung cancer risk, but beta-carotene supplements increased it in smokers — ATBC and CARET trials.)
- **Prefer whole-food evidence** (food-level RCTs, long-term cohorts) when it exists. Single-nutrient math is a fallback, not the default.
- **Label coverage honestly.** Anywhere nutrient totals are shown, include a short note: "Nutrient numbers cover ~150 measured compounds. Foods contain thousands more that aren't tracked."
- **Personal measurement beats prediction.** The app's answer to dark matter is empirical: log the food/diet change, measure markers before and after (bloodwork, CGM, wearables), and show what actually changed in this person. The body responds to every compound, named or not.

### Implementation (v0.7)
- **Food data:** `knowledge/foods/cofid-foods.json`, a curated extract of McCance & Widdowson's CoFID 2021 (UK, Open Government Licence). USDA was the first choice but `*.usda.gov` was unreachable when this was built; CoFID is an EU-region national table, which this file allows. Values are copied, never estimated: "Tr" → 0, "N"/missing → left out. Portions are labelled examples. To add foods, extend the generator's code list and re-extract from the CoFID spreadsheet; don't type values by hand.
- **Evidence claims:** `knowledge/evidence/*.json` (`EvidenceClaim` in `packages/shared/src/core/types.ts`). Each has a `lever`, `kind` (food / diet / supplement / habit; supplements may not list foods), the measured `outcome`, `grade` + `whyThisGrade` checked against the cited abstracts, and `markers` with `helpsWhen`. Biomarker `affectedBy` must mirror them (a test enforces it).
- **Safety:** `SAFETY_LIMITS` in `packages/shared/src/core/foods.ts` hides foods per portion (vitamin K ≥ 60 µg with blood thinners, potassium ≥ 300 mg with kidney disease, retinol ≥ 300 µg in pregnancy); `hideWhen` hides whole claims. Levers are not shown next to a critical value.
- Grades and wording are a first draft by the developer, not reviewed by a clinician yet.

### What the feature does
- Use a food composition database (e.g. USDA FoodData Central bulk download, or EU national tables) shipped as a static dataset. Portion math ("75 g strawberries ≈ X mg vitamin C") is computed, not generated, and is labeled as measured-nutrient-only.
- Recommendations are **levers with evidence grades**, not prescriptive meal plans: "Low ferritin → heme iron sources, vitamin C with meals, tea/coffee away from meals (grade: moderate)."
- Example meals are framed as examples that hit a nutrient amount, never as "the optimal meal for you."
- Every nutrition suggestion links to a "test it on yourself" flow: baseline measurement → change → follow-up measurement (see N-of-1 below).
- Respect the safety rules above.

### N-of-1 experiments (v0.8)
- User defines: change (e.g. "add 2 kiwis daily"), outcome markers, baseline period, intervention period.
- App reminds when to re-measure and shows before/after with the measurement noise for that marker (e.g. typical lab and biological variation), so users can tell a real change from noise.
- Results are framed as "what happened in you," never generalized as evidence for others.
- **Implementation:** `packages/shared/src/core/experiments.ts`. "Before" = results in the 120 days up to the start; "after" = results from start + re-test interval (to 30 days after an ended experiment). Several results per side are combined with a geometric mean. Noise band = log-normal reference change value: Z 1.96 · √(1/n1 + 1/n2) · σ, σ from CVI and CVA (Fraser 2011, PMID 21958344; Fokkema 2006, PMID 16873298). CVA is assumed to be 0.5 × CVI.
- **CVI data:** `biologicalVariation` (optional) on a biomarker file feeds `rcvBand`. The EFLM Biological Variation Database values once there (61 markers) were **removed on 2026-11-23** (the user's decision): EFLM's terms need written permission, an agreement and a fee to put its content in software. EFLM replied on 2026-11-24 (a formal agreement and EUR 6,000 a year); the user declined, and the values were also removed from the git history (rewritten and force-pushed 2026-11-24). What was used and where is in `docs/eflm-biological-variation.md`; never add EFLM values or copy its estimates, and tests use made-up values (`withVariation` in `tests/helpers.ts`). Without published values, `personalBand` estimates normal variation from the person's own results when there are at least 3 before and 3 after: pooled spread of the log values, t value for the degrees of freedom (`t95`, wider for small samples), `bandFrom: "personal"` shown in the UI and to Brain. With fewer results the watch says "needs more results" rather than guess.
- Creating an experiment also creates a log entry; ending it ends that entry. Experiments are in backups (backup format version 2; version 1 files still restore).
- **Habits** (`#/habits`, `apps/web/src/app/pages/HabitsPage.tsx`, `packages/shared/src/core/habits.ts`): the log and the experiments are one page. A habit is a log entry; it can **watch markers**, which is an experiment linked to it (`protocolId`), so "what changed" uses the same tested comparison. Habits may start up to a year ahead (planned). Marker suggestions come from words in the habit and its protocol snapshot items (`HABIT_HINTS`, mirroring the evidence levers plus a few medicines with a known lab effect); the person always picks. Nothing is compared automatically for every marker: with many markers, about 1 in 20 would look changed by chance. `chosenOn` records when markers were picked; picked after the "after" results existed → shown as "a hint, not a test" (`pickedAfterResults`). Editing or stopping a habit updates its watch (`saveHabit`); deleting removes both (`deleteHabit`). A new habit can start from the person's own words, **a meal** (fills name and diet type; `#/habits?meal=<id>`, the meal page's "Start as a habit") or **a protocol** ("Start protocol": `startPlan`, one named habit containing all items from the chosen day). `#/log`, `#/experiments` and `#/experiments/new` open Habits; the detail page stays at `#/experiment/<id>`.

## Conventions

- TypeScript strict, no `any` in `packages/shared`.
- Every function in `packages/shared/src/core` has tests. Every knowledge entry has sources.
- Package manager is **Bun** (`bun install`, `bun add`). Don't use npm, and don't commit a `package-lock.json`. Add a dependency to the workspace that uses it (`bun add <name> --cwd apps/web`); shared tooling (TypeScript, Vitest, turbo) lives in the root `package.json`.
- **Biome** (`biome.json`) lints and formats TypeScript, JavaScript, CSS and JSON config: double quotes, semicolons, trailing commas, 2 spaces, 160 columns. Markdown, YAML, `knowledge/`, test fixtures and generated JSON are left alone. `bun run format` writes; `bun run check` (and CI's `biome ci`) only reports. Turned off on purpose: `noNonNullAssertion` (`!` with `noUncheckedIndexedAccess`), `noArrayIndexKey` (key by id when a list can be edited or reordered), `useMathMinMax` (its fix breaks ISO date strings), `useSemanticElements` and `noNoninteractiveTabindex` (SVG roles; scrollable regions must take focus), `useIterableCallbackReturn`, `noUndeclaredEnvVars`; hooks report missing dependencies, not trigger keys. Suppress one line with `// biome-ignore <rule>: <reason>`, never without a reason. `.git-blame-ignore-revs` hides the one-time reformat (`git config blame.ignoreRevsFile .git-blame-ignore-revs`).
- Small PRs. Run `bun run check`, `bun run test` and `bun run build` before committing (`bun dev` starts the page and the server for trying changes). After adding a knowledge file, delete `node_modules/.vitest-cache`: Vitest's file cache doesn't see new files matched by `import.meta.glob`. (`bun run test`, not `bun test`: the latter is Bun's own runner, not Vitest.)
- UI copy: plain language, short sentences, explain every abbreviation once.
- Accessibility: keyboard navigable, readable contrast, works at 360px width.
- UI building blocks (Base UI underneath; don't hand-build these): `SegmentTabs` (`components/SegmentTabs.tsx`) for a row of tabs; `Fold`, `More` and `Rows`/`Row` (`components/disclosure.tsx`) for anything that opens and closes, never `<details>` (closed panels stay findable with hidden="until-found"; `reveal()` opens them for in-page links); `SimpleSelect` (`components/UnitSelect.tsx`) for dropdowns, never a native `<select>`; `Button`/`LinkButton` with `variant` (`link` for text-only actions). Shared looks live in `components/ui.tsx`: `Card` / `cardStyles`, `linkCardStyles` (clickable tiles), `dialogStyles`, `eyebrowStyles` / `eyebrowSmallStyles` (the small uppercase label), `inputStyles`, `labelStyles`.
- Motion: short and calm (150–360 ms, `--ease-soft`), defined in `apps/web/src/index.css` (`animate-enter`, `animate-enter-next/back`, `animate-fade`, `stagger`). Everything stops for `prefers-reduced-motion` (durations, delays, repeats); the chart checks it too.
